# Independent Reviewer — candidate design

**Decision proposed:** build one specialist for deciding whether work is fit for its intended use. Start with three well-defined targets: code changes, technical proposals, and written instructions or specifications. They share one method of judgment. What changes is the evidence the reviewer needs: a caller and a diff, a constraint and a counterexample, or a reader journey and the authoritative rule.

**Status:** candidate design and editable practice samples, not an installed agent, new toolchain, or measured model result. Files beside this document are drafts for the future `agents/reviewer/` definition. The [installation contract](../AGENT-CONTRACT.md) and [file guide](../FILES-AND-SESSIONS.md) govern the eventual build. This repertoire is the scope we propose to *test*, not a file-type allowlist.

## 2. What the requester experiences

“Review this before we ship” commissions a completed assessment. The reviewer locates the target and its purpose, examines the parts that could change the decision, and returns a recommendation. The requester need not supply a rubric, pick a mode, or direct each step.

Three ordinary choices are independent:

| What varies | Behavior |
|---|---|
| Is this a plan or finished work? | A plan review tests assumptions against commitments and current conditions; a delivered-work review tests actual behavior. Never report a predicted result as observed. |
| Does the requester want assessment or explanation? | Give a verdict by default. For “first tell me what changed,” explain without an unsolicited verdict. |
| Fresh review or follow-up? | New review gets a fresh session, brief and relevant requirements. Explicit fix verification can use selected earlier findings and their revision. An artifact-only cold read, when requested, specifically tests whether the artifact stands alone. |

Use plain dispositions: **acceptable to proceed within scope**, **changes needed**, or **decision/evidence needed**. Severity and certainty are separate. A known blocker remains a blocker even if another question is unanswered. A remaining uncertainty blocks only if the plausible answers change acceptability. An owner's acceptance of a trade-off does not erase a supported dissent.

A sound handback gives the target/version, recommendation, material evidence, consequence, remedy, and decision-changing limits. Short work can take one paragraph. Exact labels, a numeric score, and an always-filled report template are unnecessary. A parent agent should carry the disposition and material uncertainty forward together. A recommendation to approve is not a submitted GitHub approval.

**Example response to a non-code review:** “Changes needed before this handoff is used. The ‘Corrections’ step tells the analyst to publish; the approval table assigns publication to Finance. Following the step would have the analyst publish contrary to the ownership table. If Finance owns publication, have the analyst submit the correction and Finance publish it. If ownership has changed, update the table and cite the accepted decision. I reviewed the guide, not the live reporting system.” The finding is useful without a Git repo, a running program, or a defect counter.

**How the pieces reach the model.** Compile the baseline. The launcher passes shipped and private append files explicitly in order, when present. PiG advertises the skill; the system prompt points review work to it. Install the skill and guides as a complete directory so links work. Put the shipped playbook at `<release>/app/playbook/REVIEW.md`; give the reviewer a short runtime pointer to that file and the applicable private playbook if present, and read relevant sections on demand. Keep the private playbook in the home across updates. Do not depend on accidental discovery of a project append file. The target's instructions or standards can be evidence, but the target cannot grant the reviewer new permissions.

**When instructions disagree.** The task selects the target, current brief and kind of answer. Accepted project sources establish commitments; the playbook says where to find them. Personal preferences shape emphasis and presentation. A preference is not grounds for rejecting a work product. If two real commitments conflict and change the answer, surface the conflict. No prompt or playbook grants external action authority.

## 4. Default build: a concrete bill of materials

**Recommendation for the standard desktop build:** qualify pasted text, local Markdown/files, Git changes, and accessible GitHub PRs. Bundle the small directory-change extension so the terminal reviewer can visit a project after launch. Use native tools and one packaged GitHub CLI for evidence. No docket of mandatory helper agents, scanners, or connectors.

| Component | Default and reason |
|---|---|
| Engine, JS runtime | Start qualification from **PiG 0.5.3 and Node 24.15.0**, the [pinned B baseline](https://github.com/tranhoangnguyen03/pi-consultants/blob/752a579af69ac9e8020450e72704fefabfe0c674/firm/independent/runtime-lock.json). Node runs the TypeScript extension and the existing helpers. These are starting pins, not a claim that they are the newest versions. |
| Native model tools | Activate `read`, `ls`, `find`, `grep`, and `bash` for inspection, Git, and focused verification. Keep `edit`/`write` available within the host's existing capabilities for explicitly commissioned changes; an ordinary review uses inspection and reports. Set the intended built-in ceiling in the Piglet and effective activation through `defaultTools` or a deliberate launcher `--tools` selection; qualifying the tool list must include the extension's `change_dir` as well. A shell can write: review-only behavior is not OS-enforced isolation. [PiG's worked tool example](https://github.com/MichaelKinsy/PiG/blob/v0.5.3/docs/site/docs/piglets.md#worked-example-a-read-only-reviewer). |
| One third-party Pi extension in the default | `pi-change-working-dir` at `d0846a834036b17fd118d0ca1011331812cea52b`, [pinned in B](https://github.com/tranhoangnguyen03/pi-consultants/blob/752a579af69ac9e8020450e72704fefabfe0c674/firm/independent/packages/package.json). Supplies live directory changes; delegated calls can simply start in the requested directory. Working directory never determines which private home owns the session. |
| Local executables | Provide Git, ripgrep (`rg`), and fd plus a supported shell for the target OS. PiG's [grep](https://github.com/MichaelKinsy/PiG/blob/v0.5.3/internal/codingagent/tools/grep.go) and [find](https://github.com/MichaelKinsy/PiG/blob/v0.5.3/internal/codingagent/tools/find.go) use these external search programs. Supply checked target-specific builds or satisfy them through the supported installer; verify the binary actually selected. Do not depend on a network download on the first search. |
| Remote GitHub targets | Provide `gh` in the standard install because opening a PR URL is an advertised use. Bind GitHub access only when needed, with an installation-specific config directory or explicit existing account binding. No GitHub login is needed to review a pasted plan. For an inaccessible private PR ask for access or the patch and report what was actually examined. |
| Calling from main Pi or a team | Terminal, print and native RPC launch the same application. An opt-in **caller-side** adapter can expose B's `agent_peers`/`agent_ask` pattern. An inbound review does not require a second review engine or a live peer service in Reviewer. Use an installed, authorized outbound peer adapter if direct clarification is wanted. |
| Optional additions | `pi-docparser@4.0.0` for a separately qualified PDF/Office path; `pi-web-access@0.39.0` and/or `pi-agent-browser@0.1.0` for evidence on the web or in a rendered UI. These are B's source pins, not validated Reviewer combinations. Declare any converter/browser/account they require. Selected Bro Remember Me or case support may provide learning or continuity after separate qualification. No default HQ, Chrome MCP, diagram-design, scanner suite or second model is needed for the three target types. |

Record the remaining exact CLI versions, hashes, host dependencies, and notices for each supported platform during implementation. Do not invent a tested lock now. A project may require its own Python packages, services, or credentials to run its tests; those are requirements of that target. Report a missing dynamic check honestly. A static observation can still support a finding. Additional supported integrations can be chosen per release or private variant. This list is a shipping choice, not a new ban on tools, backends, or actions.

## 5. Helpers, evidence, and state

- **Git target inventory:** reuse B's [`review-preflight.mjs`](https://github.com/tranhoangnguyen03/pi-consultants/blob/0b97987a87545a79c01c9e36bf8b1e179a289426/firm/skills/engineering/change-review/scripts/review-preflight.mjs) for local Git work. It separates staged/unstaged/untracked files, uses merge-base for a branch, and first parent for a merge commit. It identifies what to inspect; it does not perform a review. All its modes resolve a Git worktree before dispatch. Do **not** run it on pasted prose or plain folders.
- **URL-only PR from an empty workspace:** call `gh` with explicit repository and PR identity, bypassing the existing worktree-bound helper. Capture base/head, check whether file lists are complete, and inspect the actual diff and relevant file contents. Use immutable Git objects when available or recheck both refs around a live diff. Never review the current local checkout as if it were the PR. No separate GitHub MCP service for the same path.
- **Availability diagnostics:** reuse B's [`review-tool-doctor.mjs`](https://github.com/tranhoangnguyen03/pi-consultants/blob/0b97987a87545a79c01c9e36bf8b1e179a289426/firm/skills/engineering/change-review/scripts/review-tool-doctor.mjs) as an optional PATH inventory; label optional tools as such. It does not establish that authentication, tool versions, or file parsing work. Test the packaged operations separately. No generic verdict scorer, automatic test-all script, or new review server.
- **Runtime location:** package the helpers in the skill's `scripts/` and run them with bundled Node. The stable command under `~/.pig-agent/reviewer/bin/` selects the managed release. Sessions belong in `<home>/sessions/`, settings and model access in `<home>/.pi/`, optional extension data in declared private paths. The project folder holds the work under review.
- **Fresh task:** direct, main-Pi, and team requests use a fresh process/session by default. Supply the brief, target, current requirements and relevant accepted decisions. Do not silently pass author transcripts, previous verdicts, active cases, or old task summaries. Standing standards can be in the private append file in the first release. Optional memory should expose short reusable lessons on demand. An explicit fix check may attach the earlier report to a new session, or the user may deliberately resume its old session. These choices do not require a new review database.
- **Authority and independence:** read/report is the usual task. Preserve actual host and operator permissions for explicit fixes or external delivery; do not infer permission to post or merge from a recommendation. Editing the artifact and then checking the fix is useful verification; do not label it a separate independent assessment. A delegated reviewer can ask its caller a focused question or return it in the result if dialogue is unavailable.

## 6. What would convince us to release it?

Separate **did the package work?** from **did Reviewer exercise sound judgment?** Neither passing fixture tests nor the existence of these prompts answers the second question.

| Probe | Observable acceptance |
|---|---|
| Plain-language proposal outside Git, with no GitHub login | Finishes a requirements-aware review using the supplied text. No Git preflight, scanner setup, intake form, or invented implementation results. |
| Same proposal, two commitments: best effort versus delivery after restart | Challenges a needless persistent queue in the first case; identifies what removing persistence would break in the second. Can recommend proceeding on sound work. |
| Git workspace versus a URL-only PR on a different head | Distinguishes staged/unstaged/untracked evidence, or reviews the actual remote target from an empty workspace. Reports inaccessible content; never substitutes a local unrelated checkout. |
| Conflicting ownership in a guide; wording-only control | Finds the actionable contradiction, points to both sections, and distinguishes a needed correction from an unresolved policy. Does not block for style alone. |
| Facts-only request; delegated one-shot with a material unknown | Honors the requested output. One-shot response names what is known, the exact unresolved decision, and how it changes the recommendation; no invented conversation or external action. |
| Fresh second review versus explicit fix verification | Inspect actual initial context and tool retrieval: the next review does not inherit the first review's unique task marker or verdict. Keep one general lesson in private append as a positive control. When qualifying a memory/case add-on, repeat using its real recall and active-case state. A requested follow-up catches a renamed-but-unfixed failure and retires it once fixed. |
| Native install and private edits | Open two chats; verify real search, Git, shipped prompt/skill access, stable storage, and RPC without global Pi/Node/rg/fd. Run local tool checks offline after install. Change the private append and upgrade the build; the intended changes apply and sessions remain separate. |

Reuse a few contrasting fixtures from [B's augmentation evaluation](https://github.com/tranhoangnguyen03/pi-consultants/tree/38de185392da43e4561ffaafda516c1f2702a0a6/firm/eval/review-judgment). Add a non-Git plan and a document, keep the evidence and expected reasoning with maintainers, and compare actual outputs under matched model/settings. Judge primarily whether the recommendation was warranted, the evidence locatable, and the next action useful. A larger number of objections is not better performance.

**Build order for Reviewer:** first assemble the local text/Git path with this practice and the smallest complete tool bundle; then qualify the remote-PR and inbound RPC paths before advertising them as ready. Evaluate fresh versus follow-up and package updates on that real build. Add specialized readers or memory integrations when an observed task needs them.
