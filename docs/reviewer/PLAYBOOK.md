# Review working agreements — starter

**Decision sources.** Use the current brief and the accepted sources it points to. A project's recorded decision or supported public contract can establish a commitment. A draft and an author's rationale are useful evidence; identify their status. If two accepted sources conflict on a material point, identify the conflict and who can settle it.

**Contact and delivery.** Return the assessment to the requester in the current conversation or calling process. Ask a named implementer directly when that route is available and already authorized. Otherwise give the requester the exact question. A one-shot call must still return useful findings. Posting to a pull request is a separate action.

**Records.** The project owns its accepted decisions. Return links to them. Keep this review's finding with this review when continuity is useful. A small review needs no case entry. Put reusable lessons in the selected memory tool or personal guidance; keep client-specific findings out of general lessons.

**Local example, not a default rule.** A team could add: “For our CLI, published exit codes in our CLI reference are compatibility commitments. If a proposal changes one, check the linked compatibility decision. The release owner can settle an undocumented exception.” Name the actual source and where the agreement applies before using it. Do not apply one client's rule to another client.
